# MIDI → 生存战争(Survivalcraft)音乐数据 转换代码审核报告

> 审核范围：`generator/midi/MidiFileDecoder.java`、`NoteDataCollection.java`、`ScSoundDataPanelRender.java`、`InstrumentInfo.java`（附带 `generator/mp3/Mp3ToMidiDecoder.java`）。
> 依据：生存战争 Sound Generator / Memory Bank 的官方说明（Recipaedia）、社区 Wiki 以及游戏反编译源码 `SoundGeneratorElectricElement.cs`、`MemoryBankData.cs`、`MemoryBankElectricElement.cs`、`AndGateElectricElement.cs`。
> 结论先行：**当前转换结果在节奏、八度、复音数、鼓、多通道文件等多个方面与游戏规则不符，生成的数据基本无法直接演奏出原曲**。详见第 2 节的逐项问题及第 3 节的复现结果。

## 1. 游戏规则（发音器 / 存储板）

### 1.1 发音器 Sound Generator（音乐板）

资料来源：
- Recipaedia 原文 & Wiki：<https://survivalcraft.miraheze.org/wiki/Sound_Generator>、<https://survivalcraftgame.fandom.com/wiki/Sound_Generator>
- 游戏源码（2.4，含 Bass）：`SoundGeneratorElectricElement.Simulate()`

四个模拟量输入（均为 0~15，即 0V~1.5V）：

| 接口 | 方向 | 含义 | 未接线默认值 |
|---|---|---|---|
| Pitch（P 端） | 左 | 音高 0~E；**F = 休止（不发声）** | 0 |
| Octave（O 端） | 右 | 八度 0~3 | 2 |
| Volume（V 端） | 上 | 响度，0 静音，F 最响 | F |
| Tone（乐器端） | 下 | 乐器码，同时也是**触发端** | 0 |

关键规则（直接摘自源码）：

1. **触发条件**：只有当 Tone 输入 **从 0 变为非 0（上升沿）**、且 Pitch ≠ 15 时才发声；同一发音器两次触发间隔 ≥ 0.08s。
   ```csharp
   if (m_lastToneInput == 0 && num4 != 0 && num != 15 && GameTime >= m_playAllowedTime) { ... }
   ```
   > 这意味着：**如果乐器端常年保持 7，整首歌只会响第一个音。** 实际电路里必须让乐器端随时钟脉冲回 0（常见做法：乐器码 与 时钟脉冲 过一个 AND 门；SC 的 AND 门是 4bit **按位与**且必须恰好两个输入，所以时钟电平必须是 F/1.5V，`7 & F = 7`，`7 & 0 = 0`）。
2. **乐器码**：1=Bell(铃) 2=Organ(风琴) 3=Ping 4=String(弦乐) 5=Trumpet(小号) 6=Voice(人声) 7=Piano(钢琴) 8=PianoLong(钢琴延音) 9=Drums(鼓) A=Bass(贝斯) F=Piano。
3. **频率公式**（非鼓）：
   ```csharp
   freq = 130.8125 * 1.0594631 ^ (pitch + 12 * octave)
   ```
   130.8125Hz = **C3 = MIDI 音符 48**。所以：

   | SC 八度 | 对应 MIDI 音符（pitch 0~B） | 音名 |
   |---|---|---|
   | 0 | 48 ~ 59 | C3 ~ B3 |
   | 1 | 60 ~ 71 | C4(中央C) ~ B4 |
   | 2 | 72 ~ 83 | C5 ~ B5 |
   | 3 | 84 ~ 95 | C6 ~ B6 |

   即 **`MIDI音符 = 48 + 12 × octave + pitch`**。pitch C/D/E(12/13/14) = 下一个八度的 C/C#/D，与 `(octave+1, 0/1/2)` 完全等价，没有额外价值。
4. **八度上限**：源码 `m_maxOctaves`，Organ 只有 C4/C5 两个采样（八度 0~2 可用），其余乐器 C4/C5/C6（八度 0~3 可用）。超出范围时音高按 ±1 个八度钳位 —— 例如 Organ 八度 3 永远发 C6，其它乐器 `(3, D/E)` 永远发 C7。Wiki 另注：Ping/Voice 的采样实际音高比名义高一个八度。
5. **鼓**：乐器码 9 时忽略 Octave，Pitch 直接选鼓：0=Snare 1=BassDrum 2=ClosedHiHat 3=PedalHiHat 4=OpenHiHat 5=LowTom 6=HighTom 7=Crash 8=Ride 9=HandClap，A~E 无声。
6. **响度**：`volume = V/15`，V=0 静音。

### 1.2 存储板 Memory Bank（M 板）

- 256 个 4bit 单元，地址 = `右输入(低4位) + 左输入(高4位) × 16`，即 0~255 线性地址，游戏内编辑框按 16 个字符一行显示（行号 = 左输入）。
- `MemoryBankData.LoadString()` 读取字符串前 256 个十六进制字符，非法字符当 0。
- 若底部接了时钟，只在时钟上升沿（≥8）刷新输出。

> 因此 M 板中**每一个格子对应电路计数器的一个节拍**。要还原节奏，转换器必须把乐曲按**固定时间步长**采样：长音 = 1 个发音格 + 若干休止格(P=F)，而不是"一个事件一个格子"。

## 2. 逐项问题

严重程度：🔴 直接导致输出错误 / 不可用　🟠 明显失真　🟡 轻微 / 代码质量

### 🔴 P1 时间轴完全丢失（无时间量化）

- 位置：`ScSoundDataPanelRender#buildGridNoteDateByTick` 第 286~315 行
- 现象：`scNoteTickList = tickData.keySet()`，**每个"出现过事件的 tick"只写 1 个格子**，与事件之间的间隔无关。二分音符和十六分音符在 M 板里占同样的 1 格。`getBaseTick(120, resolution, 30)` 算出来的 `baseTick` 从未被使用（并且 `bpm / 60` 是整除，BPM<120 时为 1 或 0）。MIDI 的 `set_tempo` 元事件也没有读取。
- 后果：README 里"播放节奏取决于电路脉冲时间"的前提是每格时长相同，但当前数据里每格代表的时长并不相同，所以**无论电路脉冲怎么调，节奏都不对**。
- 复现：`rhythm.mid`（二分 C4、八分 E4、八分 G4、四分 C5）→ 输出 `C 4 7 C`，4 个音等长。

### 🔴 P2 不同乐器的格子互不对齐

- 位置：同上，`tickData` 是**每个乐器自己的** tick 集合。
- 后果：乐器 A 的第 i 格和乐器 B 的第 i 格对应的是各自第 i 个事件的时刻，而不是同一时刻。而游戏里所有 M 板由同一个计数器驱动，第 i 格必须是同一时刻 → 多乐器曲目必然错位。

### 🔴 P3 Note-Off 被当作音符写入，抢占声部、复音数翻倍

- 位置：`MidiFileDecoder#handMidiMessageNoteOff` 第 389~400 行；`buildGridNoteDateByTick` 第 279~306 行
- 现象：NOTE_OFF 事件会在对应 tick 塞入一个 `ScNoteData(15,0,0)` 占位；"演奏数量"（需要几块板）= 同一 tick 的列表长度最大值，占位也被计入；同一 tick 上 NOTE_OFF 通常排在 NOTE_ON 前面，于是占位占住第 0 块板，真正的音符被挤到第 1 块板。另外 NOTE_ON+velocity 0 这种常见的"松开"写法却被直接忽略（第 266 行），两种写法行为不一致。
- 后果：
  - 单声部旋律被拆到两块板：`scale.mid`（单声部 C 大调音阶）→ 板 0 只有第 1 个音，其余 7 个音都在板 1。
  - 需要的发音器数量翻倍：`菊次郎的夏天.mid` 真实最大复音 **6**，工具要求 **12** 块板（板 2~11 几乎全是休止）；`Flower Dance.mid` 真实 **5**，工具要求 **9**。
  - 游戏里一个音一旦触发就按采样自然衰减（约 1s），只能被同一发音器的下一个音打断、无法单独停止，NOTE_OFF 对 SC 没有意义，只应用来判断"这一格是否休止"。

### 🔴 P4 C / C# / D 三个音被整体抬高一个八度

- 位置：`MidiFileDecoder#handMidiMessageNoteOn` 第 283~289 行
  ```java
  if (m <= 2) { pitch = m + 12; } else { pitch = m; }
  noteData.octaves = baseOct;   // 八度没有 -1
  ```
- 原因：pitch 12/13/14 在游戏里 = **下一个八度**的 C/C#/D。写成 `pitch+12` 的同时八度必须 `-1`（被注释掉了），否则这三个音比同八度的 E~B 高了 12 个半音。`saveNoteData` 第 375 行只对钢琴在"压缩后"的八度上补了 `-1`，压缩系数 ≠ 1 或八度为 0 时仍然错；其它乐器完全没有补偿。
- 复现：`scale.mid` C4 D4 E4 F4 → `(C,0) (E,0) (4,0) (5,0)`，实际听感是 **C5 D5 E4 F4**。
- 建议：删掉 `m <= 2` 分支，直接 `pitch = note % 12`。

### 🔴 P5 `updateNoteInfoData` 笔误，最高八度被写成最大响度

- 位置：`NoteDataCollection#updateNoteInfoData` 第 59 行
  ```java
  maxOctave = Math.max(maxVelocity, octave);   // 应为 Math.max(maxOctave, octave)
  ```
- 后果：`maxOctave` 变成 max(最大响度, 最后一个音的八度)，既不单调也不正确。`octaveDiff` 随之错误 → 八度压缩系数错误。
- 复现：`scale.mid` 日志"最高八度：12"（velocity 100 → 响度 12）；`octaveDiff=7`，`perOctaveTake=0.5`，结果 **C4 和 C5 被映射成同一个音** `(C,0)`。

### 🔴 P6 乐器状态按 Track 而不是按 Channel 跟踪；鼓通道识别依赖 Program Change

- 位置：`MidiFileDecoder#decodeSequence` 第 207~237 行（`int instrumentCode = 0` 是 track 局部变量）
- 原因：MIDI 的 Program Change 作用于**通道**。Format 0 文件（16 个通道都在一个 track，很常见，仓库自带的两个示例就是 format 0）或一个 track 含多通道时，后面的 Program Change 会覆盖前面通道的乐器；并且通道 9（第 10 通道）按 GM 规范永远是鼓，很多文件不会给它发 Program Change，此时鼓被当作钢琴解析音高。
- 复现：`multich.mid`（ch0 钢琴、ch1 小提琴、ch9 鼓，format 0）→ 钢琴集合 **0 个音**，钢琴、小提琴、鼓的全部音符都进了"弦乐器"，共 8 块板。
- 建议：维护 `int[16] channelProgram`，NOTE_ON/OFF 用 `message.getChannel()` 查；`channel == 9` 无条件视为鼓。

### 🔴 P7 鼓全部静音（整数溢出）

- 位置：`ScSoundDataPanelRender#saveNoteData` 第 364~366 行 + `handMidiMessageNoteOn` 第 291 行
- 原因：鼓分支不会调用 `updateNoteInfoData`，`maxVelocity` 保持 `Integer.MIN_VALUE`；`SC_VELOCITY.length - MIN_VALUE` 溢出为负数，`velocity` 变成负数，`SC_VELOCITY[Math.max(0, velocity - 1)]` 永远取 `'0'`。
- 复现：`drums.mid` 所有鼓格 V 端全是 `0`。

### 🔴 P8 鼓的音符映射 `note % 10` 与游戏鼓表无关

- 位置：`handMidiMessageNoteOn` 第 295 行
- 现象：GM 36 底鼓→6(HighTom)，38 军鼓→8(Ride)，46 开镲→6(HighTom)，49 Crash→9(HandClap)，51 Ride→1(BassDrum)。
- 建议映射（GM 打击乐音符 → SC 鼓 pitch）：

  | GM 音符 | 名称 | SC |
  |---|---|---|
  | 35, 36 | Bass Drum | 1 |
  | 37, 38, 40 | Side Stick / Snare | 0 |
  | 39 | Hand Clap | 9 |
  | 42 | Closed Hi-Hat | 2 |
  | 44 | Pedal Hi-Hat | 3 |
  | 46 | Open Hi-Hat | 4 |
  | 41, 43, 45 | Low / Low-Mid Tom | 5 |
  | 47, 48, 50 | Mid / High Tom | 6 |
  | 49, 52, 55, 57 | Crash / Chinese / Splash | 7 |
  | 51, 53, 59 | Ride / Ride Bell | 8 |
  | 其它 | — | 用 0(Snare) 或 F(休止) |

### 🟠 P9 八度映射：线性"压缩"而非移调，且忽略绝对音高

- 位置：`saveNoteData` 第 369~381 行
- 现象：把该乐器出现过的最低八度映射到 0，再按 `3/(diff+1)` 或 `4/(diff+1)` 线性缩放。缩放系数不是 1 时，相邻两个八度会被合并成同一个八度（音程被破坏）；而且每个乐器各自从 0 开始 → 贝斯和旋律被挤到同一个音区，编配关系丢失。
- 建议：按游戏公式做**绝对映射** `scNote = midi - 48`，对每个乐器选一个整八度移调量 k（使落入 0~47 的音符最多），仍超限的音按八度折叠回范围内。这样所有音程、不同乐器之间的相对音区都能保留。

### 🟠 P10 八度上限写死为"钢琴 0~3，其它 0~2"

- 位置：`saveNoteData` 第 371~380 行、`handMidiMessageNoteOnByAverageOctave`
- 现象：2.4 版（工具已经包含 2.4 才加入的 Bass=A）中除 Organ 外全部乐器都支持八度 0~3，Bass 也是 0~3；只有 Organ 是 0~2。另外 `(octave 3, pitch D/E)` 会被游戏钳到 C7，`pitch >= 12` 的写法在最高八度不可用。

### 🟠 P11 GM 乐器映射表 0 基 / 1 基混用，名称表错位

- 位置：`MidiFileDecoder` 静态块；`InstrumentInfo.MIDI_CODE_TO_INSTRUMENT_NAME`
- 现象：
  - 表中大部分按 0 基（0=大钢琴，40=小提琴，56=小号 ✔），但"人声"用了 54/55：0 基下 54=Synth Voice、**55=Orchestra Hit**（被当成人声），而最常见的 52 Choir Aahs / 53 Voice Oohs 没有映射。
  - `InstrumentInfo` 名称表是 1 基（1=Acoustic Grand Piano…128=Gunshot），但 `getInstrumentNameByCode(shortMessage.getData1())` 传的是 0 基 program → "发现不支持的乐器"日志里的名字全部错位 1（例如 program 24 尼龙吉他会显示"探戈手风琴"）。
  - 覆盖面太小：吉他 24~31、弦乐合奏/合成弦乐 48~51、Slap/Synth Bass 36~39、马林巴/木琴/管钟/扬琴 12~15、钢片琴 8、口琴 22、圆号/铜管合奏 60~63、长笛类 72~79、Synth Lead 80~87 等常见音色都被直接丢弃；Harpsichord/Clavinet(6/7) 映射到"钢琴延音"也不贴切（它们是短促的拨弦音色）。

### 🟠 P12 多个 GM 音色映射到同一 SC 乐器时分页被拼接

- 位置：`ScSoundDataPanelRender#renderPanel` 第 96~101 行
- 现象：`scNoteData` 以 GM program 为 key，program 0 和 1 都→钢琴，`noteDataMap.computeIfAbsent(new NoteNameTuple(7, num)).addAll(...)` 把第二个 program 的分页**追加**到第一个 program 的分页后面 → "钢琴1"的第 N 页可能是另一条轨道的开头，页码与时间错位。
- 建议：解析阶段就按 **SC 乐器码** 合并（同时结合 P2 的统一时间轴）。

### 🟠 P13 乐器端（Tone）常量输出，与触发规则冲突

- 位置：`saveNoteData` 第 368 行 `instrumentStrData.append(instrumentCode)`
- 现象：乐器端 256 格全是 `7`。按 1.1 第 1 条，发音器只在 Tone 0→非0 时发声，直接接 M 板只会响第一个音。这不算纯粹的代码 bug，但工具没有任何说明，用户照着"复制到对应 M 板"的说明接线必然失败。
- 建议二选一：① 文档/说明页写明乐器端需与时钟脉冲（F）过 AND 门；② 提供选项：休止格写 `0`，并把每个音符后强制留一格 0（会把最小步长限制为 2 格）。

### 🟡 P14 鼓组 Program Change 判断顺序错误

- 位置：`handMidiMessageProgramChange` 第 373~386 行
- 现象：先用 program 查 `GM_TO_CUSTOM`，再把通道 9 的 `originInstrument` 改成 -1。鼓组 program 为 8/16/24/25/32/40/48 等时会误报"不支持的乐器"（名字还错位），只是靠 NOTE_ON 分支兜底才没丢数据。

### 🟡 P15 其它

- `decode()` 只接受小写 `.mid` 后缀，`.MID`、`.midi` 被拒绝（第 141 行）。
- `handMidiMessageNoteOnByAverageOctave`、`getBaseTick`、`SC_VELOCITY`（与 `SC_NOTES` 完全相同）是死代码 / 冗余。
- 响度归一化 `velocity += 16 - max` 再 `[velocity - 1]`，等价于 `v + 15 - max`，可读性差；`ceil(v/127*15)` 让 MIDI velocity 1~8 都变成 1，建议 `round` 后 clamp 到 1~15。
- `showMidiInfo` 打印的 `getDivisionType()` 为 0.0 没有意义；SMPTE 分辨率的文件没有处理。
- `Mp3ToMidiDecoder`：在线转换会把用户的音频上传到第三方 `api.ai-midi.com`（建议在界面上提示）；本地转换 `isSimilarPitch` 用绝对 2Hz 判定相同音（应按半音/音分比较，否则低音区颤音会被切成很多碎音），且只能处理单音旋律。

## 3. 复现记录

使用仓库原始 `MidiFileDecoder` + 原样复制的 `buildGridNoteDateByTick/saveNoteData` 逻辑（去掉 JavaFX）运行，每列是 M 板中的一格：

```
  乐器:7 演奏数量:2 最高八度:12 最低八度:5 最高响度:12       ← P5：最高八度=响度
  plate 0  P: C F F F F F F F F                              ← P3：第 1 个音被单独拆到板 0
  plate 1  P: F E 4 5 7 9 B C F
           O: 0 0 0 0 0 0 0 0 0                              ← P4/P5：C4 与 C5 都成了 (C,0)，D4=(E,0) 比 E4=(4,0) 高八度

  tick : 0  960 1200 1440 1920
  plate 1  P: F 4 7 C F                                      ← P1：四个时值不同的音各占 1 格

  GM 0  -> SC 7 : 0 cells                                    ← P6：钢琴没有任何音
```

## 4. 修复建议（方案概要）

### 4.1 最小修复（不改数据格式，只修明显 bug）

1. P4：`pitch = note % 12`，删掉 `+12` 分支和 `saveNoteData` 里的 `-1` 补偿。
2. P5：`maxOctave = Math.max(maxOctave, octave)`。
3. P6/P14：按通道维护 program，通道 9 恒为鼓。
4. P7：鼓也更新 `maxVelocity`，或归一化前判断 `maxVelocity > 0`。
5. P8：加入 GM 打击乐 → SC 鼓映射表。
6. P11：修正 54/55 → 52/53/54，名称查询 `+1`；补全常用音色映射。
7. P10：八度上限按乐器（Organ 0~2，其余 0~3）。
8. P3：NOTE_OFF 不再写入占位（只在该 tick 没有任何 NOTE_ON 时才产生休止格）。

> 最小修复后旋律/鼓/多通道都能对上，但 **P1/P2（节奏与多乐器对齐）仍然不对**。

### 4.2 推荐重构（解决 P1/P2/P3/P9/P12）

1. **统一时间网格**：读取 tempo map，把 tick 换算为时间；选择步长（建议可配置：1/4 拍、1/8 拍… 或固定毫秒），所有乐器共用同一网格，格 i ⇔ 时刻 i×步长；在日志里给出电路时钟周期（`60 / (BPM × 每拍步数)` 秒）和需要的 M 板数量。
2. **声部分配**：同一格内同一乐器的多个音分配到不同的板（复音数 = 同格最大音数，而不是事件数）；没有音的格写 `P=F, V=0`。
3. **绝对八度映射 + 整八度移调 + 折叠**（见 P9），八度上限按乐器。
4. 解析阶段按 **SC 乐器码** 聚合（而不是 GM program），避免 P12。
5. 乐器端：默认恒定乐器码并在说明页写明需与时钟 AND；或提供"休止写 0"选项（见 P13）。
6. 响度：`clamp(round(v / 127 × 15), 1, 15)`，可选按乐器归一化。

### 4.3 说明页（DescribeController）建议补充

- O 端范围：风琴 0~2，其余 0~3；SC 八度 0 = C3（MIDI 48），1 = 中央 C 所在八度。
- 乐器端为触发端，需要 0→非0 的跳变；时钟电平须为 F。
- 鼓的 P 端取值表（0~9）。

### 5.1 新的转换流水线


| 文件 | 说明 |

### 5.2 逐项对照

| 问题 | 处理 |
|---|---|
| P1 无时间量化 | 每个音按 `round(tick × 每拍格数 / resolution)`（固定毫秒步长时按 tempo map 换算成时间再取整）落到网格；长音 = 1 发音格 + 休止格；日志给出时钟周期 `步长时长 / 每步格数` |
| P2 乐器格子不对齐 | 所有乐器共用网格，第 i 格 = 第 i 步；所有声部页数相同、第 N 页时间对齐 |
| P3 Note-Off 占位 | 不再记录 NOTE_OFF / velocity=0；声部数 = 同格最大音数（菊次郎 12 → 6，Flower Dance 9 → 5） |
| P4 C/C#/D 抬高八度 | `pitch = rel % 12`，`octave = rel / 12`，只有乐器最高音（如钢琴 C7）用 `(最高八度, C)` 表示 |
| P5 maxOctave 笔误 | 相关代码整体删除 |
| P6/P14 乐器状态按 Track、鼓通道识别 | 16 个通道各自的 program 数组；通道 9 恒为鼓，Program Change 不再误报 |
| P7 鼓静音 | 响度统一 `clamp(round(v / 上限 × 15), 1, 15)`，上限 = 127 或乐曲最大力度（归一化） |
| P8 鼓 `note % 10` | GM 打击乐音符映射表（底鼓→1、军鼓→0、闭/踩/开镲→2/3/4、桶鼓→5/6、Crash→7、Ride→8、拍手→9…），非鼓通道上的 Taiko/Melodic Tom/Synth Drum/Reverse Cymbal 也映射为鼓；无对应鼓声的音符丢弃并记录 |
| P9/P10 八度压缩、上限写死 | 绝对映射 `MIDI = 48 + 12×O + P`；每种乐器选整八度移调量（旋律音权重 2、每移调一个八度扣 3%，收益不明显时保持原调），仍超限的音按八度折叠；八度上限按乐器（风琴 0~2，其余 0~3） |
| P11 GM 表错位 | 新表全部 0 基，人声 52/53/54，名称查询 `program + 1`；覆盖全部 128 个音色 |
| P12 同乐器分页拼接 | 解析阶段即按 SC 乐器聚合 |
| P13 乐器端常量 | 提供两种模式：恒定（说明页写明需与时钟 F 过 AND 门；钢琴可直接接时钟）/ 脉冲（音后补 0，免 AND 门，每板 128 步）；每步时长 < 80ms 时提示 |
| P15 其它 | 后缀大小写、SMPTE 文件、变速提示、死代码清理；`Mp3ToMidiDecoder` 上传第三方前提示，`isSimilarPitch` 改为按音分（50 音分）比较 |
